# 项目语义化版本维护

## 版本来源与阶段

- 本流程建立时的版本基线为 `3.0.0-rc.0`。后续始终读取 `package.json` 的 `version`，不要反复恢复基线。
- 项目目前处于测试阶段，内部测试版本格式为 `MAJOR.MINOR.PATCH-rc.N`。`N` 是从零开始、无前导零的整数；展示或标签可以使用 `v` 前缀，包版本不加 `v`。
- 用户已确认：测试迭代只递增 `rc.N`，例如 `3.0.0-rc.0` → `3.0.0-rc.1`；确认是 patch 发布才递增补丁号并移除测试标识，例如 `3.0.0-rc.2` → `3.0.1`。不要将 patch 发布写成 `3.0.1-rc.0`，也不要仅移除后缀得到 `3.0.0`。确认 patch 发布即已确认使用无 rc 的版本，无需再次询问是否正式发布。
- `package.json` 是唯一版本来源。同步 `package-lock.json` 的顶层 `version` 和 `packages[""].version`，不要修改依赖包版本。“关于”窗口从包文件读取版本，不维护额外常量。

## 提交前确定更新类型

1. 检查工作区、暂存区及相对 `HEAD` 的实际变更，确定本次提交范围；结合 `docs/` 中的接口约定，评估对 API、状态结构、配置、存储及用户操作的兼容性。
2. 区分修复、新能力和不兼容变更。提交前向用户简述兼容性结论及建议版本，不能只根据 `feat:` / `fix:` 前缀决定版本号。
3. 用户在本次指令或适用的持续指令中已明确更新类型或目标版本时，直接遵循，无需重复询问。否则先完成代码修改和验证，再询问“本次作为内部测试更新还是 patch 发布？”并给出两个具体候选版本；收到回答前不最终写入版本、不提交。对新增功能或不兼容变更，说明原因并提供适当的 minor/major 候选，不能把不兼容改动默认为 patch。
4. 若用户指定的版本低于当前版本或与兼容性结论冲突，解释具体冲突并澄清，不能擅自改成其他版本。

## 递增规则

以下示例以 `3.0.0-rc.2` 为当前版本：

| 更新类型 | 下一版本 | 适用情况 |
| --- | --- | --- |
| 内部测试更新 | `3.0.0-rc.3` | 同一目标版本内的兼容迭代，包括文档、重构、修复和待测试功能 |
| patch 发布 | `3.0.1` | 确认发布兼容修复；增加 patch 并移除 rc 后缀 |
| minor 发布 | `3.1.0` | 确认发布兼容功能；增加 minor、patch 归零并移除 rc 后缀 |
| major 发布 | `4.0.0` | 确认发布不兼容变更；增加 major、minor 和 patch 归零并移除 rc 后缀 |

同一核心版本的内部更新只增加 `N`。若兼容性变化需要切换测试目标核心版本，先与用户确认，再从新目标的 `rc.0` 开始。正式版需要再次开启内部测试时，先确定更高的目标核心版本，不能追加 rc 导致版本倒退。

## 写入、验证与提交

- 每次创建新的 Git 提交都必须包含版本更新，文档、配置和技能修改也适用。仅编辑、检查、测试文件时不递增版本；本技能不构成创建提交、推送、打标签或发布的授权。
- 确认目标版本后使用精确版本命令，例如内部更新：

  ```bash
  npm version 3.0.0-rc.3 --no-git-tag-version --ignore-scripts
  ```

  示例仅适用于上表基线，实际执行时替换为确认后的版本。避免直接运行 `npm version patch`，它对预发布版本的处理不等于本项目的 patch 规则。也不要使用会自动创建提交或标签的默认模式。
- 检查两份 JSON 的三个版本字段相等，审阅差异，确认未改动依赖，并运行 `git diff --check`。按变更范围运行测试和构建，无法运行时说明原因。
- 将版本文件和本次相关修改纳入同一个提交；先审阅暂存差异，避免混入其他工作。提交失败重试时复用已经确认并写入的目标版本，不再递增一次。
- 提交说明中记录版本变化（例如内部测试 `3.0.0-rc.2 → 3.0.0-rc.3`，或 patch 发布 `3.0.0-rc.2 → 3.0.1`）、更新类型、兼容性结论及验证结果。完成后报告最终版本与提交标识；未经授权不额外推送、打标签或发布。
